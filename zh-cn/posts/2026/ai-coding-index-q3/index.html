在我自己和身边的开发者里，只要手上有 AI 编程工具，几乎没人再一行一行手写代码了。打开 X 或者任何一个技术社区，用 AI 写代码的分享也随处可见。

可是翻开 20 个大型开源项目的 git 历史，2026 年第三季度只有 13.2% 的提交写明了 AI 参与，一年前是 1.4%。这 13.2% 里有 63% 来自 VS Code 一家，不算 VS Code 只有 5.7%。Rust、Kubernetes、Django 接近 0。

我不认为这些项目的贡献者没在用 AI。更可能的是：很多人用了，但没写。

用了，但没写
#

同一个项目里，写不写完全看人。

pandas 从 2026 年 1 月起要求贡献者披露 AI 使用，而且要写清工具、模型和版本。本季度一位长期核心维护者的 625 条提交里，606 条写了 Co-authored-by: Claude，约 97%。去掉他，其余贡献者只有 8.1% 的提交写了。CPython 和 Git 也是这样：九成署名提交来自同一个人，去掉这一位，分别只剩 2.4% 和 0.8%。

规定一样，能用的工具也一样，有人几乎每条都写，大多数人一条不写。我很难相信这些项目里只有一两个人在用 AI。

VS Code 是另一面：3,597 条署名提交来自 129 位作者，前 5 位只占 32%。Copilot 相关工具会自动写上 Co-authored-by: Copilot，于是大部分人的提交都带着它。写不写，很大程度上取决于工具替不替你写。

0 也不全是隐瞒
#

公平地说，有些 0 有别的原因：

  • Rust 在 2026 年 8 月采用的 LLM 政策允许用 LLM 分析、检查、审查代码，但不允许用来「创作」，生成代码只在实验规则下有条件允许。它的 0 有一部分是规定限制出来的。
  • PyTorch 要求在 PR 里披露；Django 也要求披露，但没有写进提交信息。这里都数不到。
  • Node.js 的规范建议提交信息里不写商业品牌名，可以写成「a closed-source coding agent」。gitstats 2.12 已经能识别这种写法。
  • Codex CLI 的公开仓库改成从 OpenAI 内部仓库导出后，原始提交里的标记全部丢了。

这些原因能解释一部分 0。但在我看来，它们解释不了「人人都在用 AI 写代码」和「只有一成多的提交写明了」之间这么大的落差。

为什么有人用了不写
#

我猜，是因为很多项目和社区还接受不了「代码是 AI 写的」。写明了，PR 可能被多问几轮，甚至直接被关掉；不写，从代码上看不出来。

可我还是不太理解。用 AI 写代码已经这么普遍，为什么还要藏着？

维护者该看什么
#

我认为，维护者不应该去追问一段代码是贡献者自己写的还是 AI 写的。该看的是贡献者能不能为这段代码负责。

遇到下面几种情况，维护者完全可以关掉 PR，不接受这次贡献：

  • 代码写得让人看不懂，或者和要解决的问题对不上；
  • 维护者问了几个很简单的问题，贡献者答不上来；
  • 贡献者的回答全是 AI 生成的，看不出他自己理解了这段代码。

用 AI 帮忙组织回答没有问题，关键是贡献者自己有没有看懂。只要讲得清楚、改得动，代码是不是 AI 写的并不重要。

说句题外话：现在不少维护者接受贡献时，也会看贡献者的 GitHub 主页。如果对方是知名的开源贡献者，代码就算有问题，维护者也可能想先合进去，因为看重的是这个人。看工具和看人，都偏离了代码本身。

我还是建议写明
#

写不写不该成为合并的门槛，但我还是建议写。维护者和以后读代码的人能知道这段代码是怎么来的；写的人多了，这份指数也才能接近真实的使用情况。

写法也需要统一。本季度看到的写法就有 Co-authored-by、Assisted-by、只写模型型号、只写「a closed-source coding agent」好几种。我维护的 commit-check 可以把这件事变成提交规则：设置 ai_attribution = "disclose" 后，它要求用 Assisted-by: 这类披露行写明 AI 参与，拒绝把 AI 写成共同作者或签名人。

怎么算「署名」
#

gitstats 的 Gallery 每周对 20 个大型开源项目的完整 git 历史生成报告。其中一项是「署名 AI 的提交」：一条提交只要满足下面任一项就被计入：

  • 作者就是 AI 账号（例如 copilot-swe-agent[bot]）；
  • 有 Co-authored-by: 指向 AI 的地址（例如 noreply@anthropic.com）；
  • 有工具留下的签名行（例如 Generated with [Claude Code]）；
  • 有 Assisted-by: / Generated-by: 这类披露 trailer，并写出了助手名字。

这里数的是「署名」。 一个标记只说明 AI 参与了这条提交，说明不了它写了一行还是全部；而没留标记的 AI 使用（行内补全、关掉 trailer 的工具）完全数不到。所以每个数字都是下限。

按生态看差异
#

AI 编程工具自身：数字最低，而且在下降
#

直觉上，做 AI 编程工具的团队应该最爱用 AI。可他们的提交里署名反而最少：

  • Codex CLI 从 3.8% 降到 0%，原因在数据管道。2026-07-10 起，公开仓库的提交改由 OpenAI 内部仓库导出（提交者是 copyberry，每条都带 GitOrigin-RevId），原始提交信息里的标记没有保留下来。
  • Aider 在 2026-05-22 之后就没有提交了，所以本季度没有占比。之前的高占比来自 Aider 把自己写成提交作者。
  • OpenCode 0.2%：gitstats 刻意不把 OpenCode 自己发版和重新生成文件的机器人账号算作 AI 助手，剩下的显式署名很少。
  • Gemini CLI 稳定在 4–6%，但季度提交量从 1,878 降到 170（原因这次没查）。

工具团队怎么提交、怎么同步公开仓库，对这里数字的影响比用不用 AI 还大。

Python 数据与 AI 栈：增长最快，但看谁在提交
#

  • pandas 66.7% 是全表最高，但 632 条署名提交里 606 条来自同一位维护者（见上文）。
  • Transformers 17.0%、PyTorch 9.7% 都在 2026-Q3 跳升（上季度分别是 4.8% 和 2.4%），这两个项目这次没有逐条核查。PyTorch 的 AI 规范（2026-07）要求在 PR 里标明，没有要求写进提交。
  • NumPy 2.0%、LangChain 1.1%、FastAPI 0.3% 一直很低。

语言运行时与系统基础设施：两极分化
#

  • Node.js 24.4%：标记几乎全是 Assisted-by: 披露（Codex、OpenCode、Claude 等），来自 40 位作者，前 3 位占 77%。Node.js 在 2026-08-12 发布了 AI 使用规范，之后两个月的署名数明显增加。这份规范还建议提交信息里不写商业品牌名，可以写成「a closed-source coding agent」：gitstats 把这样的提交算作「未具名助手」，本季度有 11 条。只写在 PR 里、不进提交的披露仍然数不到，所以 Node.js 的数字依然是下限。
  • CPython 18.0%：244 条中 220 条来自一位核心开发者。CPython 的规范是「在 PR 里披露 AI 使用欢迎但不强制」。
  • Git 7.3%：2026 年才出现，70 条里 63 条来自同一位维护者，标记大多是 Assisted-by: Opus 4.7 这类只写模型型号的披露。
  • nginx 5.5%：本季度只有 91 条提交，5 条署名，样本很小。
  • Rust ≈0%、Kubernetes 0%：Rust 的 LLM 政策见上文。

编辑器、Web 框架与包管理
#

  • VS Code 57.1%：和 pandas 不同，这是广泛分布的：3,597 条署名来自 129 位作者，前 5 位只占 32%。一年前它的署名主要是 Copilot 代理自己作为作者提交；现在主要是人写的提交带 Co-authored-by: Copilot。要注意两点：VS Code 和 Copilot 都出自 Microsoft，这是在用自家工具；而且 Copilot 相关工具会自动写这个 trailer（VS Code 有一个 git.addAICoAuthor 设置，2026-04 曾短暂默认开启，现在默认关闭）。
  • React 19.8%：一年里从 0 到 20%，但本季度只有 162 条提交，32 条署名。
  • Homebrew 2.4% 基本平稳。Django 0%：Django 要求贡献者披露 AI 使用，但披露没有进入提交信息（推测留在 PR 或工单里）。

方法与局限
#

  1. 只统计显式署名，是下限。 行内补全不留痕迹；很多工具的 co-author trailer 可以关掉；有人会手动删掉；只写在 PR 里的披露也不进提交。这些都数不到。

  2. 署名不等于 AI 写的代码。 一个 Co-authored-by: Claude 可能是 AI 写了全部改动，也可能只是帮忙改了一个测试。报告里所有的「占比」都是「署名 AI 的提交占全部提交的比例」。

  3. 各项目的披露规范不同，占比不能直接比较。 本季度看到的情况包括：

    • 要求披露，并且写进了提交：pandas（要求写清工具和模型）；
    • 要求或鼓励披露，但建议匿名或只写在 PR 里：Node.js（建议提交里不写品牌）、PyTorch（写在 PR 里）、Django（要求披露，但没有进入提交）；
    • 欢迎但不强制：CPython；
    • 限制使用：Rust（不允许用 LLM「创作」，代码只在实验规则下有条件允许）；
    • 没有找到项目级规定，但工具会自动加 trailer：VS Code。

    一个项目占比高，可能是用得多，也可能只是披露得认真；占比为 0，可能是没用，也可能是写在了别处。比较同一个项目随时间的变化更可靠。

  4. 少数人能决定一个项目的数字。 pandas、CPython 和 Git 的署名提交，九成以上来自各自一位核心贡献者。

  5. 数据管道会改变数字。 Codex CLI 的公开仓库改成从内部导出后，标记全部消失。squash 合并时是否保留 PR 描述、机器人是否改写提交信息，都会影响结果。

  6. 小样本。 React（162 条）、nginx（91 条）、Gemini CLI（170 条）的季度提交很少，几条提交就能改变好几个百分点。

  7. 项目选择。 这 20 个项目是 Gallery 的固定样本，偏向大型、知名、英文社区的项目，不代表整个开源世界。其中 4 个是 AI 编程工具自身。

  8. 重新统计。 Gallery 在 2026-10-15 冻结了本季度的快照。之后 gitstats 2.12 补上了几种此前识别不出的署名写法：只写模型型号的 Claude（如 Opus 4.7）、Grok、IBM Bob、Pi，以及「a closed-source coding agent」这类不写名字的披露。本文按 2026-10-24 的新规则重新统计了这 20 个项目，与冻结快照相比，Node.js 从 22.6% 变为 24.4%，Git 从 5.1% 变为 7.3%，合计占比不变（13.2%）。重新统计也包含了季度结束后才合入、作者日期在季度内的提交。

如何复现
#

1. 直接用 Gallery 的数据（本报告的全部汇总数字都来自其中这 20 个项目）：

curl -O https://shenxianpeng.dev/gitstats/gallery/ai.json

ai.json 里每个项目的 quarters 就是本文表格里的季度数字：ai_assisted 是署名提交数，commits 是全部提交数。

2. 对任意仓库重新统计：

pipx install gitstats
git clone https://github.com/pandas-dev/pandas.git
gitstats pandas report-pandas

生成的 report-pandas/summary.json 里，ai_assisted.by_month 和 ai_assisted.commits_by_month 是每月的署名数和总提交数，按季度加总就得到本报告的数字。

3. 查看匹配规则： 哪些写法算作 AI 署名，全部写在 gitstats/assistants.py 里。本文的逐条核查也是用这套规则，对每个仓库按作者日期列出署名提交的作者分布和标记类型。
